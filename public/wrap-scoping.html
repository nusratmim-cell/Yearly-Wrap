1Eligibility & cohort — who gets a wrap

Rule: one wrap for every student with an active paid enrolment overlapping the window (1 Jan–20 Dec 2026), minus test/internal accounts. Judged over the window, not on launch day.

2Multiple programme enrolments (tech’s question)

Verified: a student can hold several programme enrolments, and the platform already keys everything per (user_id, academic_program_id) — enrolment rows, the old quarter/year review (route takes a programme identifier), and rank (PhaseRank_*/SubjectRank_*). So one wrap row per (student, programme) is consistent with how Shikho already works.

The nuance to decide: not every metric is per-programme —

MetricGranularityWhy
Study time · active days · streak · video · quizzesPer student (same across all their programmes)VERIFIED warehouse aggregate grouped by user_id (no programme split); mcq tables per user
Live-class attendance (joined/held) · classesPer programmeVERIFIED lessons by academic_program_id
Rank / percentile · favourite teacherPer programmeVERIFIED per-phase/subject rank in results-reporting
Recommendation (→ O2): ship one wrap per student. Use whole-year per-student totals for the big numbers, and for the per-programme bits (attendance, rank, favourite teacher) use the primary programme = the one most-active in 2026 (most active days / study time; tie → most recent enrolment). Keep PK (user_id, program_id) where program_id = that primary. One clean story per student; no duplicate rows; the single home banner has an unambiguous target.
Edge caseHandling
Which wrap does the one home banner open?The primary programme’s (rule above). Others optional later via a “switch” affordance. O2
Student active in 2+ programmes almost equallyTie-break deterministically: most active days → most study time → most recent enrolment. Reproducible across reruns.
Batch vs programmeScope to academic_program_id (the programme), not batch. A student changing batch within a programme is still one programme.
How did last year pick for multi-programme?Confirm with the ST-25781 owner — the old review was per-programme, so match or deliberately improve. O2

5Rank & score reuse — and the bugs NOT to inherit

Reuse the analytics results-reporting scoring so the wrap matches the app: overall = classPct*0.5 + examPct*0.5, both clamped ≤100; grade A+/A/A-/B/C/D/F at 80/70/60/50/40/33; level good≥80 / moderate≥60 / else. Rank/toppers come from the leaderboard Redis ZSET (per phase/subject).

WATCH — do NOT inherit these verified known bugs from results-reporting:
Known bugWhat to do instead
Last-week rank == current rank (fake week-over-week delta)Don’t show a rank “delta” unless we compute a real one. WATCH
Dummy data in GetQuarterData/GetSubjectDataNever call the placeholder paths; read real aggregates only. WATCH
Hardcoded 0: AnimatedLessonsWatched, PracticeQuizzesParticipatedCompute these from the warehouse for the wrap; don’t reuse the 0 fields. WATCH
Three divergent performance-level scalesPick one scale for the wrap and apply it consistently.
VERIFIED all four are documented limitations in the results-reporting spec (status “partial”).

6Learner-type stamp

Rule: one stamp per full-wrap student, cohort-relative (z-score arg-max) over real axes (rhythm, intensity, method, accuracy, pace, attendance, focus, clock). Grounded in real signals; no model to reuse (m1_baseline_model is lead-scoring, not segmentation).

Edge caseHandling
Zero-variance axis (σ=0)NULLIF(σ,0) → axis drops out of arg-max. No divide-by-zero.
Student with no graded questionsAccuracy/Pace/Focus NULL → excluded from their arg-max; stamp still resolves from rhythm/intensity/method/attendance.
No reliable hour bandDrop the Clock axis (raw user_activities.date is noisy — silent now()-fallback). O8
Fresh-Start students in the baselineExcluded from μ/σ so sparse users don’t skew the cohort. They get no stamp (2-slide deck).
One axis dominates for most studentsConfig can drop/down-weight it — no app release. Monitor the stamp histogram post-run.

7Badges — two systems + the low-activity floor

A · Wrap tier badges (we compute): metric clears a threshold in wrap_tier_config; DAG t7 assigns the highest rung. Built as ladders with a low starter rung + universal badges so every student earns ≥1 and nobody sees an empty shelf. B · Learning badges (gamification already awards; wrap only reads from StudentBadges).

Edge caseHandling
Low-activity student → empty badge shelf?No. Starter rungs (যাত্রা শুরু ≥1 day, Quiz/Video/Class starters ≥1) + loyalty (শিখোর সাথী) guarantee ≥1 badge. Never render “0 badges”.
Too many badgesShow the highest rung per ladder, 3–4 max, achievement-first.
Learning-badge calculationNot recomputed — gamification service owns it (percent-of-completion buckets, speed/accuracy, app-usage). Wrap needs only the StudentBadges → datafuse pipe. O7VERIFIED gamification badge specs
Thresholds wrong / lopsidedAll config — retune with no release. Guardrail: no tier swallows >60% of students (check distribution once).
