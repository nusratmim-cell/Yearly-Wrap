The short version

  • We already shipped a yearly review once. Last December (ST-25781) we deployed a dual-mode "2025 Year Wrapped" + "Q4 Review" — 8 swipeable native cards, a rank, engagement text, and a native share sheet. That is the thing the new Wrap replaces.
  • The 2026 Wrap is a bigger, more personal story (Spotify-Wrapped style), paid students only in release 1, built on a tiered data layer so Product can re-tune messaging without an engineering release.
  • Most of the numbers already exist in the datafuse Postgres warehouse (user_activity_duration_agg, the mcq_user_* tables, student_attendees, lessons, programs, user_activities). The gaps are: Shikho AI, QR scans, eBook opens, badges, and best-exam detail — these live in service databases and need piping into the yearly job.
  • The main build is a data layer, not a UI. One nightly/one-shot batch job → one Wrap record (JSON) per paid student → one API → a web story screen the Android app opens, plus share images and public links.
  • Direction C3 "Journey" is the recommended look; the prototype is live at shikho-year-end-wrap.vercel.app.

01What the yearly review is today

The "current yearly review" is the Q4 & Year-End User Review Report (ST-25781), deployed Dec 2025–Jan 2026. It is a dual-mode feature driven by purchase history, and it is the direct predecessor of the 2026 Wrap.

Segment A — "Year Wrapped"

Students who bought the full-year syllabus. Stats aggregated Jan–Dec. Festive pink-gradient theme, confetti, "2025 Unlocked".

Segment B — "Q4 Review"

Students who bought only Q4. Stats for Oct–Dec only, with a Q4-vs-Q3 comparison. Reuses the Q3 "beige" theme.

How it works (mechanics worth reusing)

  • Entry: a home-screen banner — "তোমার ২০২৫ কেমন গেলো?" (yearly) / "এই তিন মাসে তুমি কেমন করলে?" (Q4) — shown when is_report_available = true.
  • Backend switch: API takes user_id, program_id, phase_id, decides report_type, and returns all slide data incl. calculated fields (engagement level, streak, final score, rank).
  • Presentation: swipeable native cards, per-slide gradients, header/footer text that changes by engagement tier (High / Moderate / Low).
  • Rank: per-program cohort rank, shown only for top 50, with Bangla ordinals; ties take consecutive numbers.
  • Share: native Android button captures a clean screenshot → Android share sheet; fallback PNG 1080×1920.

02The 2026 Wrap, and what's new

Per SC-1737: at year end, every paid student gets a short, personal, shareable story of their 2026 on Shikho (1 Jan → a December cut-off). The spec deliberately defines only the data layer — Product/design build any wrap idea on top, tuned by tiers, with no new engineering request.

Design principles baked into the spec

  • Tiers & thresholds are settings. Every metric can be split into tiers (High/Moderate/Low, cut-offs configurable) and has a minimum below which the frontend may hide it — changeable with no app release.
  • Per-subject and per-month splits are kept so "personal insights" (e.g. "your accuracy rose in the months you joined more live classes") can be derived later without new data work.
  • Success metrics: open rate, finish rate, share rate, and January-2027 return rate vs. non-openers.

04Data we have vs. data we need to get

Already have (warehouse)

  • Active days, dates, streaks — user_activity_duration_agg
  • Study time & durations by 7 content types, per day/month
  • Video time & counts
  • Quizzes, questions, correct, accuracy, by subject/chapter — mcq_user_*
  • Live class attendance & teachers — student_attendees, teacher_attendees, lessons
  • Live-exam scores — user_activities
  • Profile & purchases — Students, Transactions, programs

Need to get / build

  • GET Shikho AI usage → warehouse (gen_ai_*)
  • GET QR scans (qr_scan_logs)
  • GET badges (StudentBadges)
  • GET best model-test detail (model_test_session)
  • GAP eBook opens — locate the log first
  • BUILD study-time-by-subject (no subject column in agg)
  • BUILD time-of-day bands, attendance rule, favourite teacher
  • GAP deep lifetime history (tables start ~late 2024)
One structural gap to flag early: the main aggregate table has no subject dimension, yet "top subject", "strongest/weakest subject" and "subject × time-of-day" are the most personal parts of the Wrap. Reconstructing subject-level study time from the per-log tables is the single biggest derivation task — worth validating with BI before committing the subject slides.

05What needs to be built

Data layer — the core of the work

Warehouse tables→ Piped service data (AI, QR, badges, exams)→ Yearly Wrap batch job→ One Wrap record / student (JSON)→ Tier settings applied
  • Yearly aggregation job — one run that, per paid student, rolls up every metric above into a single record for 1 Jan → cut-off. Natural home: a new DAG in data_pipeline_bronze alongside the existing user_activity_* and mcq_session_agg DAGs.
  • Pipe the gap sources into that job: Shikho AI (gen_ai_*), QR scans, badges, best model-test; locate eBook opens.
  • Subject-level reconstruction join (video + live class + quiz logs) with a reconciliation check vs. the agg totals.
  • Tier/threshold config — a settings store (tiers, cut-offs, minimums per metric) read at record build or read time, changeable with no release.
  • Paid-student eligibility + minimum-activity rule (decision pending) and the is_report_available flag, as in 2025.

API

  • A Wrap endpoint (gateway) returning the per-student record, like the 2025 review API (user_id, program_id, phase_id → data points + calculated fields). Reuse its rank and composite-score logic.

Frontend & app

  • Web story screen (recommended C3 "Journey") the Android app opens — faster to iterate than native cards.
  • JS ↔ Android bridge for the share action (reuse 2025's native screenshot → share sheet), PNG 1080×1920 share images, and public share links so a friend can open a shared card.
  • Entry points: home banner "তোমার ২০২৬", launch-day push notification, shared-link landing. (The home-banner slot is the same one the 2025 review used.)
  • Share privacy: option to hide the student's name on the public card; agree what may appear + whether to attach a referral code.

What we can reuse from 2025 (don't rebuild)

Native share sheet + screenshot capture · engagement-tier header/footer text pattern · per-program cohort rank (top 50, Bangla ordinals, tie handling) · the report-availability flag & home-banner entry · the by-user/program/phase API shape · composite-score calculation.

06Open decisions & risks

Decisions (Product / leadership)

  • Direction: confirm C3 Journey (recommended) — borrow B3's marksheet share card.
  • Who gets it: paid only vs. trial too; minimum activity to qualify.
  • Definitions: a "study day", live attendance (live only vs. live+recording), a "quiz".
  • Cut-off date in December; launch window 26–31 Dec.
  • Which new slides: percentile, most-improved subject, topics that got stronger.
  • Sharing rules + referral code; web screen vs. native.

Risks / to verify with BI & Eng

  • No subject column in the agg table → subject slides depend on a reconstruction that must reconcile.
  • History depth: lifetime totals under-count for pre-2024 students.
  • Gap sources (AI, QR, eBook, badges, model-test) not confirmed in the warehouse.
  • student_attendees.duration across rejoins; multiple teacher rows per class.
  • Does lessons hold every 2026 live class (incl. pre-new-program)?
  • Spec tables are generated from code and can be stale — verify against production before building.
